# Контекст проекта

Мобильный веб-дашборд с инструкциями для водителей грузовиков компании HEAD, HDLG. Водитель открывает одну ссылку, находит тему и читает PDF / документ / видео прямо в приложении. Файлы живут на Google Диске — здесь только витрина.

Боевой адрес: https://siahead2017-png.github.io/Driver_Instructions/

**Язык общения и интерфейса — русский.** Владелец — не программист: объяснять просто, давать готовые команды целиком, честно разделять «проверено» и «не проверено».

## Главное правило

**Никакой сборки и никаких зависимостей.** Чистые HTML/CSS/JS (ES-модули): GitHub Pages отдаёт как есть, владелец правит контент через веб-редактор GitHub, проект не протухает. **Не предлагать** React, Vite, Tailwind, npm-пакеты.

## Окружение

Сборки, тестов и линтера в проекте нет — только эти команды:

```powershell
.\serve.ps1                                                                     # локальный сервер -> http://localhost:8000
node --check assets/js/app.js                                                   # синтаксис-чек после правки любого .js
node -e "JSON.parse(require('fs').readFileSync('data/instructions.json','utf8'))"  # валидность JSON после правки контента
node -e "JSON.parse(require('fs').readFileSync('data/guide.json','utf8'))"         # то же для гида
```

- **Нет рабочего Python** (`python` — заглушка Windows Store). Node.js есть (v24) — годится для `node --check` и смоук-тестов, но npm-зависимостей в проект не тянуть.
- Локальный сервер — `serve.ps1` (PowerShell `HttpListener`, порт задаётся `-Port`); обязателен, т.к. `fetch()` не работает из `file://`. Отдаёт файлы с `Cache-Control: no-store`, так что кеш `?v=` — забота только продакшена (GitHub Pages / телефон), не локального сервера.
- **`.ps1` держать ASCII-only**: PowerShell 5.1 читает файлы без BOM как ANSI, кириллица ломает парсер.
- Растровую графику генерировать через GDI+ (`System.Drawing`), не Pillow.

## Модель данных

Плоские `items` + `categories` (намеренно — проще искать и дописывать). `category` → `categories[].id`; `subtopic` — необязательная группа; `categories[].subtopics` задаёт порядок групп; `type`: `pdf|doc|sheet|slide|image|video|link`. `important: true` — рендерится в отдельной секции «❗ Важно» первым блоком на главной и подсвечивается красным (`.card--important`) везде, где карточка встречается. Справочник полей — в [README.md](README.md).

## Виджет-калькулятор (`calc.js`)

Плавающая кнопка `.calc-fab` → модалка `.calc` (`z-index: 60`), две вкладки: «Время и топливо» и «Остатки топлива в баке».

**Время:** `driveMin = dist/speed*60`; паузы = `9 × p9Count` (степпер, максимум 5) + чекбоксы 24/45/2 ч + своя пауза. Обязательные перерывы по регламенту ЕС осознанно не считаем — только отмеченное водителем.

**Топливо:** «Тягач (по км)» = `дист/100 × расход` (дефолт 27 л); «Двигатель на стоянке» = `часы × 2,5 л/ч` (константа зашита, не показывается); «Итого прицеп» = `totalMin/60 × расход` (дефолт 1,8 л/ч). Общего «Всего» нет — заправляются раздельно.

**Остатки в баках:** марка чипами MAN/DAF/VOLVO, у каждой два бака, литры = `см × lPerCm`:

| Марка | Бак 1 | Бак 2 | Полный / линейка |
|---|---|---|---|
| MAN | 580 л, 8,65 л/см | 580 л, 8,65 | 67 см / 70 см |
| DAF | 845 л, 14,08 | 355 л, 5,58 | 60 см / 64 см |
| VOLVO | 570 л, 8,77 | 650 л, 10,00 | 65 см / 71 см |

Коэффициент DAF-1 выведен из ёмкости (845/60), не взят с ценника. Сантиметры хранятся по каждой марке отдельно — переключение марки не теряет замеры.

**Запас хода (км), под «Всего в баках»:** `(всего литров − резерв 100 л) ÷ расход тягача × 100`. Резерв (`RESERVE_L`) — топливо «на дне» бака, которое сознательно не учитываем в запасе хода, чтобы водитель не заглох на подъёме в горах при почти пустом баке. Расход берётся с поля «Тягач (по км)» вкладки «Время и топливо» (`truckEl`, дефолт 27 л/100 км) — если водитель меняет его там, запас хода считается уже по новому значению; `onInput()` пересчитывает `calcTanks()` при любой правке на вкладке «Время и топливо», не только на вкладке баков. Под цифрой — текстовая расшифровка (`calc-tanks-range-note`), какая норма и какой резерв взяты в расчёт.

**Состояние:** `localStorage` ключ `di:calc`, TTL 5 мин, всё в `try/catch` (приватный режим).

- **Хранение** — `di:bans:cargo` (массив кодов). «Обычный груз» — НЕ код, а
  пустой массив: своей записи не имеет, кнопка рисуется активной, когда массив
  пуст (`cargoHTML()`). Включение любого тумблера гасит «Обычный груз» просто
  тем, что массив перестаёт быть пустым; выключение последнего — зажигает его
  обратно тем же способом. Пустого «ничего не выбрано» на экране не бывает.
- **`cargoState(row, cargo)`** — состояние ОДНОГО ряда-запрета относительно
  выбранного груза: `exempt` (весь груз входит в `cargo_exempt`), `unchecked`
  (`cargo_checked` пуст — «нет данных», это НЕ то же самое, что «исключений
  нет»), `permit` (что-то только по `cargo_permit` — красный остаётся),
  `none` (сверено, автоматических исключений нет). Проверка — «освобождён
  ВЕСЬ груз, а не хоть что-то»: везёт фрукты и заморозку, а акт освобождает
  только фрукты — рейс остаётся под запретом.
- **`status()` не запускает эту проверку вообще, если `cargo` пуст** —
  «Обычный груз» ведёт себя ровно как экран до Фазы 6. Если запущена и ВСЕ
  ban-строки дня — `exempt`, светофор становится 🔵 (`light: 'exempt'`,
  `LIGHT_ICON`/`LIGHT_RANK`/`.bans__row--exempt` в CSS) независимо от времени
  окна — исключение снимает риск на весь день, а не на конкретный час. Если
  хоть одна строка `unchecked` — весь день красный с подписью «нет данных об
  исключениях» (даже если другая строка была бы `exempt` — осторожность важнее

  только по разрешению» через `withCargo()`.

  [Можно без разрешения: ...] (акт/параграф в конце)` — подробности и
  правило для НОВЫХ строк см. `TRUCK_BANS_EU/CLAUDE.md`, раздел «Формат
  `note_ru`». Фронтенд со своей стороны получил `noteHTML()` вместо прямого
  `esc(r.note_ru)` в `rowDetailHTML()` — ищет по тексту `note_ru` слова
  «Нельзя:» / «Можно без разрешения:» / «Можно по разрешению:» / «Можно:»
  строго в начале строки (первой или после `\n`, т.е. и в склеенных
  карточках с несколькими правилами) и оборачивает их в `<strong>`. Порядок
  в `NOTE_LABELS` важен: длинные варианты идут раньше «Можно:», иначе
  короткий вариант перехватит совпадение первым. Живые источники (Испания
  `es_dgt.py`, Тироль `at_tirol.py`) генерируют `note_ru` в коде, не в
  листе — их текст этот шаблон не затронул, они и так были без параграфов
  закона впереди. `bans.js?v=10`.
- **Закреплённая карточка «Варшава — транзитный запрет» (12.08.2026).**
  Владелец назвал этот запрет критически важным для парка отдельно от
  остальных стран — грузовики HEAD/HDLG всегда идут через Варшаву транзитом
  и никогда не заезжают внутрь города. `warsawPinHTML()` рисуется В САМОМ
  НАЧАЛЕ `paint()`, ДО `routeHTML()` — единственная карточка на экране,
  которая не зависит ни от выбранных стран маршрута, ни от периода поездки:
  показывается всегда, чтобы водитель не пропустил её, забыв отметить
  Польшу. Юридический факт (порог 16 т, часы, ссылка на источник) читается
  из уже загруженного CSV — ищет строку `country === 'PL' && title_ru ===
  WARSAW_TITLE` (в CSV нет `rule_id`, поэтому поиск по стране+заголовку;
  строка `pl-warsaw-c16` заведена в `TRUCK_BANS_EU`, подробности —
  `TRUCK_BANS_EU/CLAUDE.md`, раздел «Варшава: зона C-16»). Текст объезда
  (кольцевая S2 / дороги 50-62-60) и SVG-схема (`warsawDetourSVG()`) —
  захардкожены здесь же, а не в таблице: это подсказка по вождению, не
  юридический факт, тот же класс контента, что `CARGO_LABELS`. Схема условная
  (не географическая карта), цвета через CSS-переменные (`var(--danger)`,
  `var(--t-sheet)` и т.д.) — подстраивается под тёмную/светлую тему сама,
  ничего не хардкожено в HEX внутри SVG. Раскрытие блока «Как ехать в
  объезд» — модульная переменная `warsawOpen` (как `routeOpen`/`legendOpen`),
  не `localStorage` — сворачивается заново при каждом визите, это
  осознанно проще, чем остальные раскрывающиеся блоки экрана. Стили —
  `.bans__warsaw-pin` в конце блока `.bans*` в `styles.css` (акцентная рамка
  `var(--danger)`, единственная такая на экране, чтобы взгляд цеплялся среди
  обычных карточек стран). `bans.js?v=11`, `styles.css?v=25`.

## Гид по инструктажу (`guide.js`)

Пошаговый разбор базы знаний — вход баннером `.guide-banner` на главной, сам гид — полноэкранный оверлей `.guide`. В отличие от `calc.js`, участвует в hash-роутинге как «виртуальный экран», т.к. должен передавать управление на карточку (`viewer`) и возвращаться на тот же шаг.

**Hash-схема:** `#/guide` (последний открытый шаг либо первый) и `#/guide/<stepId>`. `app.js`: `route()`/`render()` знают только `'category'`/`'item'`, всё остальное безопасно уходит в `renderHome()` — если там появится новый `else if`, перепроверить, что `'guide'` по-прежнему не перехватывается.

**Push/replace:** открыть гид с баннера / открыть карточку из шага → обычная навигация, пишет запись в history. «Далее»/«Назад»/чип блока внутри гида → `history.replaceState` + локальный ререндер — не пишет запись (иначе «Назад» не выходил бы из гида за один тап). Закрыть — `history.back()` + запасная кнопка «на главную» на случай прямой ссылки без предыдущей записи.

**Показ/скрытие** — через `hidden`, не только z-index (`.guide` = 45, между `calc-fab` 40 и `viewer` 50): иначе элемент ловит фокус с клавиатуры позади открытой карточки (`.calc-fab[hidden]` тоже явно прописан в CSS, т.к. `display:flex` специфичнее `[hidden]`). `is-locked` (общий класс блокировки скролла у `viewer`/`calc`/`guide`) — `hideGuide()` снимает его только если `viewer.hidden === true` в этот момент.

**Данные**: `data/guide.json` — отдельный файл (опечатка в гиде не должна ронять главную/поиск). Схема: `{ blocks: [{ id, title, icon, steps: [{ id, title, text: [...], items: [...item.id], confirm }] }] }`. `items` резолвятся через `typeMeta` из `drive.js`; несуществующий id рендерится как «Материал недоступен». `confirm` — если есть, на шаге чекбокс, отметка пишет прогресс.

**Прогресс**: `localStorage`, ключ `di:guide`, без TTL. `{ current, done: {stepId: true} }`. Чекбокс — единственное, что пишет/стирает `done` (`markDone`/`unmarkDone`); кнопка «Далее →» заблокирована, пока `done[step.id]` не выставлен (`syncNextBtn`), проверка продублирована в `goDelta()`.

**Нельзя перепрыгнуть вперёд мимо непройденных шагов** — ни чипом блока, ни прямой ссылкой `#/guide/<id>`. `firstIncompleteIndex()` — индекс первого шага с `confirm` без отметки; `resolveStepId()` подменяет более дальний запрошенный шаг на этот граничный. Встроено в `goToStep()` (значит, и в чип, и в «Далее»/«Назад») и в `showGuide()` для прямых ссылок (с `history.replaceState`, чтобы адресная строка не осталась битой). Шаги до границы открываются свободно.

Последний шаг («Далее →», как и все — намеренно не «Готово», чтобы инструктаж не воспринимался завершённым до подписи) переводит на `#/register`, не закрывает гид.

**Вход в гид гейтится «данными сначала»:** `syncFromHash` требует `hasDraft()` (`di:register:draft`, пишет `register.js` на `#/start`) — без черновика редирект на `#/start`. Баннер на главной по той же причине ведёт на `#/start` для новичка и прямо в `#/guide` для вернувшегося с черновиком. Подробности потока — в разделе «Регистрация после инструктажа».

Контент адаптирован из `Driver_Briefing` (формулировки уже согласованы с владельцем), плюс блоки, которых там нет (отчёты отдела учёта, фотофиксация транспортного контроля).

## Регистрация после инструктажа (`register.js`)

**Два этапа в одном оверлее `#register`.** Данные идут ДО гида, чтобы водитель прошёл электронный инструктаж перед устным, а не сбегал после. `app.js` не знает ни `'start'`, ни `'register'` — оба уходят в `renderHome()`, как `'guide'`.
- `#/start` — приветствие (`WELCOME_HTML`) + данные (компания/ФИО/дата/e-mail), `renderDataForm()`, кнопка «Начать инструктаж →». Гейтов нет: это точка входа во весь инструктаж. По кнопке `validateData()` → `saveDraft()` (`di:register:draft`) → `#/guide`.
- `#/register` — согласие + подпись, `renderSignForm()`, кнопка «Закончить инструктаж, отправить подтверждение». Здесь собирается payload из черновика + подписи.

**Поток:** баннер на главной → `#/start` (если черновика ещё нет) → гид → «Далее →» на последнем шаге ведёт на `#/register` → отправка. Вернувшийся с черновиком идёт баннером сразу в `#/guide` (welcome только новичку — логика в `guide.js`).

**Гейты (строго «данные сначала»):**
- Вход в гид: `guide.js::syncFromHash` требует `hasDraft()` (`di:register:draft`); нет → редирект `#/start`. Симметрично тому, как `register.js` читает `di:guide`.
- `#/register`: `firstIncompleteGuideStep()` (независимая асинхронная проверка — сам грузит `data/guide.json`, сверяет с `di:guide`): строка (id шага) → редирект `#/guide/<id>`; `false` (данные не загрузились) → `#/guide` без шага; `null` (гид пройден) → дополнительно проверяется `loadDraft()`, нет черновика → `#/start`, иначе показать форму подписи.

**Координация `is-locked`/`calc-fab` с гидом** — зеркальная: `hideRegister()` проверяет `hidden` и у `#guide`, и у `#viewer`, не трогает их, если один уже открылся. Работает благодаря порядку `<script>` в `index.html` (`guide.js` раньше `register.js`).

**Поля (этап `#/start`, `renderDataForm()`):** компания трудоустройства (радио-карточки с логотипом, `COMPANIES` — `HEAD`/`HDLG`), Фамилия/Имя отдельно, e-mail необязателен (`validateData()` проверяет формат только если заполнено; пустой — `confirm()` в `handleSubmit()` на этапе подписи предупреждает, что письмо не придёт, но данные всё равно уходят). Поля префилятся из `di:register:draft`, если водитель вернулся на `#/start` (валидация подписи здесь НЕ выполняется — подпись на втором этапе).

**Дата рождения** — два способа ввода в одно и то же текстовое поле `#reg-birth-text`: маска (`inputmode="numeric"`, `maskBirthInput()` сама расставляет точки) и тоггл «Выбрать по шагам: год → месяц → день» с тремя `<select>` (год первым, список дней пересчитывается по году/месяцу через `daysInMonth()`). `parseBirthInput()` проверяет, что дата реально существует (`new Date()` не должна «перетечь» на соседний месяц). `validateData()` требует возраст 18–90 лет и что дата не в будущем.

**Подпись — полноэкранная.** Маленькое поле `.register__pad` в форме — кнопка-превью (`<img>`, не canvas), тап открывает `#sig-full` (отдельный оверлей, z-index 65, **не участвует в hash-роутинге** — временное состояние уже открытой регистрации, не отдельный экран). `SignaturePad` создаётся один раз лениво на `#sig-full-canvas` (`el.hidden = false` обязан произойти до создания — иначе `getBoundingClientRect()` даст 0×0). Канвас статичный, не пересобирается с формой — `renderSignForm()` чистит его при каждом входе на `#/register`, а «Заполнить ещё раз» — дополнительно (в связке с полным сбросом, см. ниже). `Escape` при открытом `#sig-full` закрывает только его, проверяется первым в общем `keydown`.

**Тёмная тема:** чернила по умолчанию почти чёрные (`signature-pad.js` → `#12161F`) — на тёмном фоне не видны. `penColor` красить нельзя: `toDataURL()` в `handleSubmit()` кладёт чернила на белый фон для PDF, светлые были бы невидимы уже в документе. Решение — CSS `filter: invert(1)` на `prefers-color-scheme: dark` (`.register__pad-preview`, `.sig-full__pad canvas`) — визуальный эффект, пиксели canvas и экспорт не меняются (проверено по `getImageData`).

**Предпросмотр текста согласия (`.register__confirm`)**: на этапе подписи (`#/register`) — блок с тем же текстом, что уйдёт в тело PDF, дублирует `Driver_Instructions_Backend/PDF_TEMPLATES.txt` вручную — при правке формулировок поправить оба места. Компанию называет из черновика (`draft.company`); на этом экране она уже не редактируется (выбрана на `#/start`), поэтому прежнего живого `outerHTML`-подмена по смене компании больше нет. `flex-shrink: 0` обязателен на этом блоке внутри `.register__body` (`display:flex`), иначе сжимается вместо собственного скролла.

**Backend подключён.** «Закончить инструктаж, отправить подтверждение» → проверка подписи → payload из черновика (`draft`) + `pad.toDataURL(...)` в `localStorage` (`di:register:last`, подстраховка на случай обрыва сети) → `fetch(ENDPOINT_URL, { headers: { 'Content-Type': 'text/plain' } })` (без preflight). Payload не изменился при разбиении на два этапа (`company/lastName/firstName/birthDate/email/signature/submittedAt`) — **бэкенд трогать не нужно**. Три состояния: «Отправляем…», «Не получилось отправить» (повтор без потери данных), «Данные собраны» (только после `{ok:true}`, тут `di:register:last` очищается) — на этом экране кнопка «Закрыть» (`location.hash = ''`) рядом с «Заполнить ещё раз».

**«Заполнить ещё раз» = полный сброс** (`clearAll()`: `di:register:draft` + `di:register:last` + `di:guide`, плюс `pad.clear()`) → `#/start`. Рассчитано на сценарий «несколько водителей подряд на одном офисном устройстве»: следующий начинает с чистого приветствия и пустого гида. Баннер на главной перерисовывается из `guide.js::syncFromHash` при уходе из гида (`paintBanner()`), иначе показывал бы старый прогресс до перезагрузки.

Серверная часть — `Driver_Instructions_Backend/Code.gs` (**вне этого репозитория и вне git вообще**, см. «Публикация» ниже). Пишет строку в Sheet (номер, фамилия, имя, дата рождения, e-mail, дата и время инструктажа, компания, ссылка на PDF через `RichTextValue`), собирает PDF из Google Doc-шаблона (свой на каждую компанию, `CONFIG.TEMPLATES.HEAD/HDLG`), подставляет плейсхолдеры через `Body.replaceText()`, шлёт письмо через `MailApp`.

**Известные особенности Apps Script (на будущее, если снова копаться в `Code.gs`):**
- Doc-шаблон обязан быть настоящим Google Docs, не загруженным Word/PDF-файлом — иначе `DocumentApp.openById()` падает с обманчивым «Документ недоступен».
- Тестировать Web App через настоящий браузер (`fetch()`), не `curl` — у curl нестабильные `411`/`502`/зависания на редиректе `script.google.com → googleusercontent.com`, хотя сервер отрабатывает нормально.
- В `Body.replaceText(pattern, replacement)` регуляркой является только `pattern`; в `replacement` экранировать нужно только `$` (бэкреференс), не остальные спецсимволы.
- Если Doc с вкладками (Tabs) экспортируется с лишней пустой первой страницей — сравнить `contentSnippet` через Drive API с заведомо рабочим документом, разница видна сразу; лечится пересозданием шаблона копией рабочего, не кодом.
- Владелец с трудом ориентируется в панели «Количество выполнений» Apps Script — диагностировать по тексту ошибки в ответе сервера (`{ok:false, error}`, виден в консоли браузера), не через Executions.

## Обратная связь водителей (`feedback.js`) и админка (`admin.html`)

Круглая кнопка `.fb-fab` над «пилюлей» калькулятора → полноэкранная форма
`#/feedback` (виртуальный экран, как `#/bans`: `app.js` о нём не знает).
Поля: имя, WhatsApp, тема (6 штук), номера тягача и прицепа, текст до 2000,
голосовое, до 6 вложений.

**Номера машин обязательны только для темы «Заявка на ремонт».** Строка
`REPAIR_TOPIC` продублирована в `feedback.js` и в `Code.gs` — обязана
совпадать буква в букву, иначе форма пропустит заявку, а сервер её отобьёт.
Поля при смене темы не прячутся, только получают звёздочку: исчезающий с
экрана введённый номер водитель читает как «данные потерялись». `plate()`
приводит номер к тому же виду, что и сервер (заглавные, любое тире → дефис),
иначе один прицеп попал бы в Таблицу тремя разными написаниями и поиск в
админке его бы не нашёл.
Каждое обращение получает номер `#TCK-0001`, падает в отдельную Telegram-группу
и в лист `TICKETS` Google Таблицы. **В бою с 11.08.2026**, `ENDPOINT_URL` в
`feedback.js` и `admin.js` заполнен и проверен сквозным тестом.

**Бэкенд — `Driver_Feedback_Backend/` (вне git, отдельный Apps Script проект,
не трогает бэкенд инструктажа).** ТЗ владельца просило Google Cloud Functions +
Firestore, но GCF не разворачивается без привязанной платёжной карты, а
привязывать её владелец не захотел — ушли на Apps Script + Таблицу. Подробности
и грабли — в `Driver_Feedback_Backend/CLAUDE.md`.

**Файлы уходят по одному, отдельными запросами** (`action:'file'` после
`action:'ticket'`). Apps Script не умеет `multipart/form-data`, файл едет
строкой base64 (+33% веса); одним запросом 20 МБ у водителя в роуминге
оборвётся и унесёт заявку целиком. Сначала уходит текст (тикет создан, номер
выдан, сообщение уже в Telegram), потом файлы — упавший переотправляется
отдельно. **Фото жмутся прямо в телефоне** (`compressImage()`, 1600 px / JPEG
0.8): снимок накладной 6 МБ → ~400 КБ.

**Голосовое.** `MediaRecorder` с обязательной проверкой `isTypeSupported()` —
Android пишет `webm/opus`, iPhone `mp4`, без проверки на одном из них запись
просто не стартует. На сервере каскад `sendVoice` → `sendAudio` →
`sendDocument`: Telegram требует для `sendVoice` строго `ogg/opus`.

**`syncFab()` — единственное место, где решается видимость обеих кнопок-FAB.**
Ориентир — класс `is-locked` на `body` (его ставят все оверлеи), а не список
id. Так сделано потому, что `guide.js`/`register.js`/`bans.js`/`calc.js` про
кнопку обратной связи не знают и прятать её не будут — иначе пришлось бы
править четыре чужих модуля, и каждый следующий экран ломал бы это заново.
Правило `.fb-fab[hidden] { display: none }` в CSS обязательно: `display:flex`
специфичнее атрибута. То же и для `.fb__form[hidden]` — без него форма не
уходит с экрана под экранами «отправляем»/«принято».

**Админка `admin.html`** — отдельная страница в корне, ссылок на неё из
приложения нет, `robots: noindex`. **Пароль проверяет сервер**, в публичном JS
его нет и быть не может; в `sessionStorage` он живёт до закрытия вкладки.
Карточки (не таблица — в обращении бывает 2000 символов и шесть вложений),
статусы Новый/В работе/Закрыт, фильтры, поиск, заметка, кнопка WhatsApp,
скачивание вложений. **Файл скачивается через сервер, а не прямой ссылкой на
Telegram**: в прямой ссылке лежит токен бота, он утёк бы в адресную строку.
`admin.js` — обычный скрипт, не модуль (импортировать нечего).

## Дизайн и анимации

## Как проверять

`.\serve.ps1` → http://localhost:8000. Валидность JSON (дубли `id`/`url`, сироты `category`); русские склонения (`plural()`); выгрузка iframe; нет горизонтального скролла на 375px. `instructions.json`/`guide.json` агрессивно кешируются — проверять с `?v=…`.

Для гида дополнительно: `history.length` не растёт при серии «Далее» (проверка `replaceState`); одна «назад» после N «Далее» выходит из гида целиком; прямая ссылка на шаг открывается сразу; `F5` посреди гида остаётся на месте; чип/прямая ссылка дальше первого непройденного шага возвращает на него.
